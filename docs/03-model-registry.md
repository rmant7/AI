# 3. Model Registry и подбор под устройство

Код: `core/src/main/kotlin/ai/localstudio/core/registry/`

## Модель ≠ runtime

```
ModelDescriptor
 ├── id, family, version
 ├── parameterCount, quantization, contextLength
 ├── languages
 ├── capabilities        ← что умеет
 ├── license, sourceUrl
 ├── benchmarks          ← reasoning / coding / vision / asrAccuracy / general
 └── bindings[]          ← как исполнять
       ├── runtime            (llama_cpp | mediapipe | mlc | onnx_runtime | …)
       ├── artifact           (.gguf | .task | …)
       ├── fileSizeBytes
       ├── requiredRamBytes
       ├── requiresGpu / requiresNpu / minAndroidApi
       └── referenceTokensPerSecond
```

Одна и та же модель может иметь binding под llama.cpp (GGUF, CPU) и под
MediaPipe (`.task`, GPU) с разными требованиями. Скорер выбирает лучший binding
для конкретного устройства сам — приложение об этом не думает.

Все бенчмарки нормализованы к шкале 0..100, «больше — лучше», включая
`asrAccuracy` (хранится как `100 − WER%`), чтобы ранжирование не зависело от
направления метрики.

## Артефакт разрешается на лету, а не зашивается

Практика показывает: репозитории квантованных моделей перестраиваются
maintainer'ами в масштабе недель — меняются имена файлов, набор предлагаемых
квантований, иногда и то, какой репозиторий считается каноническим для семейства.
Имя файла, зашитое в приложение при сборке, устаревает за месяцы (одно семейство
прошло три нумерованных релиза за считанные месяцы).

Поэтому каталог пиннит **семейство**, а конкретный файл разрешается в момент
просмотра. Правила выбора — `ArtifactResolver`, чистая функция без сети:

```
1. отбросить многотомные артефакты ("model-00001-of-00003.gguf")
   — скачать только первый том значит получить обрезанную модель,
     которая сломается позже и непонятнее
2. выбрать по приоритету квантования:
   Q4_K_M → Q4_K_S → Q4_0 → IQ4_XS → Q3_K_M → Q5_K_M → Q8_0
3. незнакомая схема именования → взять наименьший файл
   (при неизвестном качестве меньший размер — безопасный выбор на телефоне)
```

Ловушка для того, кто будет писать HTTP-слой: на Hugging Face реальный размер
крупного файла лежит в `lfs.size`, а верхнеуровневый `size` — это размер
LFS-указателя. Прочитать не то поле — получить каталог моделей по 130 байт.

## Сколько памяти нужно: замер и оценка

`requiredRamBytes` в binding'е — **опционально**, потому что каталог, собранный
из model hub, знает размер файла и больше ничего. Если замера нет,
`effectiveRequiredRamBytes` даёт заведомо завышенную оценку (файл × 1.3):
веса — основная, но не единственная часть расхода, сверху ложатся KV-кэш,
активации и копии загрузчика. Флаг `isRamEstimated` стоит показывать в UI —
разница между «измерено» и «прикинуто» существенна.

Первый же реальный замер на устройстве должен заменять оценку.

## Device Profile

«Пять лучших моделей» — величина, не имеющая смысла без устройства.

```
DeviceProfile
 ├── totalRamBytes / availableRamBytes
 ├── availableStorageBytes
 ├── cpuCores, androidApiLevel
 ├── supportedRuntimes
 ├── hasGpuDelegate, hasNpu
 └── performanceIndex     ← 1.0 = эталонное устройство
```

```
usableRamBytes = min( max(total × 0.35, свободно × 0.6), total × 0.55 )
```

Считать бюджет от **свободной** памяти — ошибка, и дорогая. Android показывает
в `availMem` «свободно прямо сейчас», удерживая при этом гигабайты в
кэшированных процессах, которые вытесняются по запросу. Замер на реальном
устройстве: 15 ГБ всего, 1.8 ГБ «свободно» — по формуле от свободной памяти
бюджет выходил 1.1 ГБ, то есть самый способный телефон получал самый маленький
бюджет. Основой служит общий объём памяти, а свободная учитывается только если
она больше.

Верхняя граница — 55% машины: в остальном живут ОС, процесс UI и другие стадии
пайплайна. Попытка занять последний свободный байт на Android заканчивается не
медленной работой, а убитым процессом.

## Два разных вопроса про память

Их легко перепутать, а отвечают на них разные данные:

| Вопрос | Вход | Ответ |
|---|---|---|
| «Стоит ли это качать?» | размер файла и **общая** RAM устройства | `DeviceProfile.classifyFit` → `ModelFit` |
| «Влезет ли это сейчас?» | `effectiveRequiredRamBytes` и **доступная** RAM | жёсткий фильтр скорера |

Тиринг до скачивания:

```
файл ≤ 14% общей RAM   → LIGHTWEIGHT
файл ≤ 35%             → RECOMMENDED
файл ≤ 55%             → ADVANCED   (запустится, но медленно и без запаса)
иначе                  → TOO_LARGE
```

Пороги щедрые намеренно: до скачивания известен только размер весов, а весам
сопутствуют KV-кэш и активации. `ModelFit` — это то, что показывается на экране
Models («Рекомендуется для вашего устройства»), а не то, по чему принимается
решение о загрузке в память.

## Формула пригодности

`SuitabilityScorer` работает в два шага.

**Жёсткие фильтры** (модель не «хуже» — она невозможна):

```
capability не поддерживается      → CAPABILITY_NOT_SUPPORTED
нет binding под доступный runtime → NO_SUPPORTED_RUNTIME
requiredRam > usableRam           → NOT_ENOUGH_RAM
fileSize > свободного места       → NOT_ENOUGH_STORAGE   (только для неустановленных)
требуется GPU/NPU, которого нет   → GPU_REQUIRED / NPU_REQUIRED
minAndroidApi выше системного     → ANDROID_API_TOO_LOW
```

Причины несовместимости возвращаются наружу, а не отбрасываются: в UI лучше
показать «не хватает 1.2 ГБ RAM», чем молча спрятать модель.

**Оценка выживших** — взвешенное геометрическое среднее:

```
quality = benchmark(capability) / 100          вес 0.5
speed   = min(1, refTps × perfIndex / 25)      вес 0.3
memory  = 1 − requiredRam / usableRam          вес 0.2

score   = exp( Σ wᵢ · ln xᵢ / Σ wᵢ )
```

Геометрическое среднее выбрано осознанно: у арифметического один почти нулевой
фактор компенсируется двумя хорошими, и модель, съедающая всю память, всплывает
наверх за счёт бенчмарков. Здесь она тонет.

`memory` — это запас, а не факт помещаемости (помещаемость уже проверена
фильтром). Модель, занявшая весь бюджет, не оставляет места ни ASR, ни
эмбеддеру, ни VLM — то есть ломает пайплайн, а не только себя. Такое право нужно
заслужить качеством.

Неизмеренные модели получают нейтральные значения (`quality = 0.6`,
`speed = 0.5`) — не поощряются и не хоронятся.

## Что это даёт

```
TEXT / LOCAL / устройство A (10 ГБ свободно)
1. text-small-4b     qual 78  speed 22 t/s  RAM 3.4 ГБ
2. text-large-8b     qual 88  speed 11 t/s  RAM 5.8 ГБ
3. vision-4b         qual 70  speed 14 t/s  RAM 3.9 ГБ

то же самое на устройстве B (4 ГБ свободно)
1. text-small-4b
   (text-large-8b и vision-4b отфильтрованы: NOT_ENOUGH_RAM)
```

Один каталог, разные списки — потому что ранжирование зависит от устройства, а
не от лидерборда.

## Discovery и обновления

```
Internet (например, HF API)
        ↓
   ModelCatalog (JSON)
        ↓
   registry.merge(catalog)  ──→ список новых моделей
        ↓
   registry.diff(capability) ──→ кандидаты на замену установленных
        ↓
        Notification  →  пользователь решает
```

Два правила, оба реализованы в `ModelRegistry`:

1. **Каталог обновляется автоматически, модели — никогда.** Иначе через полгода
   приложение занимает сотни гигабайт.
2. **Merge не может ничего удалить или деинсталлировать.** Установленная запись
   сохраняет состояние и путь; обновляются только метаданные. Это покрыто
   тестом `a catalog refresh cannot uninstall a model`.

`diff` сравнивает версии по числовым сегментам, поэтому `3.10` новее `3.9` —
строковое сравнение здесь даёт обратный и неверный результат.

## Загрузка

Многогигабайтная загрузка по мобильной сети обязана переживать обрыв связи, а не
начинаться заново. Проверенная на практике схема:

```
скачивание → файл ".part"
обрыв      → HTTP Range с той позиции, где остановились
backoff    → экспоненциальный, сбрасывается при любом реальном прогрессе
отказ      → только после N попыток подряд, не передавших ни одного байта
успех      → переименование ".part" в целевой файл
```

Ключевая деталь: попытка, передавшая хоть что-то, обнуляет счётчик неудач.
Иначе плохая сеть отменяет загрузку, которая на самом деле движется.

Файл на диске именуется по **стабильному id модели**, а не по имени файла из
репозитория, — иначе после переименования артефакта на стороне репозитория
приложение перестаёт находить уже скачанную модель и качает её заново.
Проверка «установлено» по одному лишь факту существования файла недостаточна:
нужен как минимум разумный минимум по размеру, а лучше — сверка с ожидаемым.

## Версии, а не замены

```
Установлено:  text-large 8B v1
Появилось:    text-large 8B v2

Рекомендация: KEEP BOTH
```

`ModelUpdate` возвращает дельты (`qualityDelta`, `speedDelta`, `ramDelta`), а не
вердикт. Новая версия не обязательно лучше для конкретной задачи: одна модель
может выигрывать в reasoning и проигрывать в скорости, и обе имеют право
остаться. Решение о выборе на каждый запрос принимает скорер, а не факт
установки.
