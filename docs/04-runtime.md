# 4. Model Abstraction Layer и Runtime Manager

Код: `core/src/main/kotlin/ai/localstudio/core/runtime/`

## Абстракция

```
                      Model API
                          │
        ┌─────────────┬───┴────┬─────────────┐
        │             │        │             │
    llama.cpp     MediaPipe   MLC       ONNX Runtime
        │             │        │             │
      GGUF          .task    свои         .onnx
```

```kotlin
interface ModelRuntime {
    val kind: RuntimeKind
    fun canRun(model: ModelDescriptor, binding: RuntimeBinding): Boolean
    suspend fun load(model: ModelDescriptor, binding: RuntimeBinding): LoadedModel
}
```

Загруженная модель отдаётся наружу как capability-специфичный handle:

```kotlin
TextModelHandle      → generate(GenerationRequest): Flow<String>
SpeechModelHandle    → transcribe(AudioRef, language): Transcript
VisionModelHandle    → analyze(ImageRef, prompt): VisionResult
EmbeddingModelHandle → embed(List<String>): List<FloatArray>
```

Добавление нового движка = одна реализация `ModelRuntime` + `RuntimeBinding` в
каталоге. Router, Context Engine, пайплайны и UI не меняются. Это же даёт
режим разработки: `REMOTE_OPENAI` (Ollama, llama-server) — такой же runtime,
только модель исполняется на десктопе.

## Почему не один runtime

- **llama.cpp** — основная масса GGUF, максимальный выбор моделей;
- **MediaPipe / LiteRT** — модели, оптимизированные под Android, доступ к GPU/NPU;
- **MLC** — отдельный путь оптимизации для части моделей;
- **whisper.cpp / sherpa-onnx** — ASR;
- **ONNX Runtime** — эмбеддеры и реранкеры.

Привязка ко одному движку означает потолок по каталогу моделей либо по
производительности. Стоимость абстракции — один интерфейс.

## Runtime Manager: кто живёт в памяти

Главное ограничение телефона: ASR + LLM + VLM конкурируют за одну и ту же RAM.

```
Мало памяти                       Достаточно памяти
────────────                      ─────────────────
Load ASR                          ASR    ─────┐
transcription                     LLM    ─────┤── все резидентны
Unload ASR                        VLM    ─────┘
Load LLM
generation
Unload LLM
```

Обе стратегии — один и тот же код:

```kotlin
runtimeManager.withModel(model, binding) { handle -> … }
```

Правила `RuntimeManager`:

1. Модель загружается при первом обращении и **остаётся резидентной** после
   освобождения — следующий вызов переиспользует её без перезагрузки.
2. При нехватке бюджета вытесняется наименее давно использованная **свободная**
   модель (refCount == 0).
3. Модель, которая прямо сейчас используется, не вытесняется никогда. Если
   бюджет не сходится без неё — `InsufficientMemoryException`, а не thrashing.
4. Модель крупнее всего бюджета отвергается сразу, ничего не выгружая.
5. `evictIdle()` — точка для `onTrimMemory()` от Android.

Поведение зафиксировано тестами в `RuntimeManagerTest`.

## Нативная сборка: три вещи, которые решают всё

Проверено на устройстве (см. [12-audio.md](12-audio.md) — источник тот же).

**1. Уровень оптимизации.** Debug-APK собирает нативный код с
`CMAKE_BUILD_TYPE=Debug`, то есть `-O0`: без инлайнинга и автовекторизации. Для
обычного кода это незаметно; для ggml, который весь состоит из тесных численных
ядер, разница `-O0` против `-O3` — десятикратная и больше. Симптом на выходе —
«одна запись обрабатывается несколько часов». Оптимизация должна форсироваться
для всех конфигураций, а не только для release.

**2. Инструкции ARM.** С выключенным `GGML_NATIVE` (а при кросс-компиляции его
обязательно надо выключать — иначе ggml нацелится на CPU сборочной машины) ggml
не добавляет вообще никаких `-march`-флагов и молча падает на базовый armv8-a
без dotprod и fp16. Квантованные matmul-ядра — доминирующая часть стоимости
инференса — рассчитаны именно на них. Нужен явный
`GGML_CPU_ARM_ARCH=armv8.2-a+dotprod+fp16`.

Плата: устройство старше ~2017 года (ARMv8.0) получит SIGILL. Правильное
решение — сборка нескольких вариантов `.so` и выбор во время выполнения
(`GGML_CPU_ALL_VARIANTS` + backend DL); это отдельная работа, требующая проверки
на реальных устройствах.

**3. Количество потоков.** Ограничивается 4, а не «все ядра». Мобильные SoC —
big.LITTLE, а ggml делит каждый matmul поровну между потоками: работа, отданная
энергоэффективным ядрам (в 2–3 раза медленнее), заставляет все остальные потоки
ждать. Четыре — хороший прокси для «кластера производительных ядер», и заодно
меньше нагрев на длинных задачах.

Отдельно стоит помнить, что первая версия этого ограничения вводилась как
*лечение* многочасовой расшифровки по теории троттлинга. Теория оказалась
неверной — виноват был `-O0`. Ограничение осталось, но по другой причине; это
хорошая иллюстрация того, зачем измерять, а не рассуждать.

## Бюджет

Бюджет `RuntimeManager` — не то же самое, что `DeviceProfile.usableRamBytes`:
второй ограничивает *одну* модель при подборе, первый — *сумму* резидентных.
Разумная отправная точка — тот же `usableRamBytes`, но его стоит уменьшать,
когда приложение уходит в фон, и пересчитывать после `onTrimMemory`.

## Чего здесь нет и не будет

Собственного inference-движка. Это отдельный многолетний проект с сомнительной
отдачей: выигрыш архитектуры — в слое над движками, а не в очередной их копии.

## Gemini Nano / AICore feasibility

Исследовано по прямому запросу — не как замена `llama.cpp` целиком, а как
возможный путь для коротких задач (memory extraction, классификация,
summarization), которые сейчас гоняют полноразмерный GGUF через `LlamaCppRuntime`
и конкурируют за RAM с остальным приложением (E5-эмбеддер, Whisper — тот самый
конфликт, из-за которого в этой же сессии чинился backfill-луп в
`AppContainer.kt`).

Часть источников (developer.android.com, developers.google.com,
android-developers.googleblog.com) недоступна из песочницы — egress-прокси их
блокирует. Ниже — то, что подтверждено через WebSearch/сторонние источники, с
явной пометкой уровня уверенности. Прежде чем что-то кодировать, часть пунктов
ниже требует реальной проверки на устройстве — это не готово к реализации.

**Вердикт (обновлено — реальный тест на Pixel 10 Pro прошёл, `AiCoreRuntime`
подключён как настоящий `ModelRuntime`-кандидат рядом с `LlamaCppRuntime`):
Gemini Nano через AICore теперь доступен как обычный провайдер в Settings
("Gemini Nano (AICore)", рядом с "Local, on-device") — включается тем же
чекбоксом, что и любой облачный провайдер. RAM-довод из п.2 ниже (общие
system-wide веса, не копия в процессе приложения) не измерен цифрами, но
достаточен как обоснование: `RuntimeBinding` для этого кандидата — те же
номинальные `fileSizeBytes=1`/`requiredRamBytes=1`, что и у любого облачного
кандидата через `servedModel()`, то есть RAM-бюджет `RuntimeManager` для
локального llama.cpp-пути этим кандидатом не затрагивается вообще.**

### Findings

1. **Архитектура доступа** (высокая уверенность, официальный источник через
   поиск): `App → ML Kit GenAI APIs → AICore (системный сервис) → веса Gemini
   Nano + аппаратный ускоритель`. Готовые API: Prompt, Summarization,
   Proofreading, Rewriting, Image Description, Speech Recognition.

2. **RAM — главный плюс для этой задачи** (высокая уверенность на уровне
   архитектуры, точные цифры не подтверждены): AICore держит **один общий
   экземпляр весов** в системной shared-memory (ion/dmabuf) на всё устройство,
   а не по копии на приложение. Это структурно другое от `LlamaCppRuntime.load()`,
   который тянет GGUF в heap процесса приложения и сидит в общем бюджете с
   Whisper/E5 — то есть Gemini Nano в принципе не должен участвовать в тех же
   RAM-войнах, которые в этой сессии чинились через `currentAvailableRamBytes()`.
   Устройство, впрочем, всё равно может не выделить его вовсе под нагрузкой —
   не проверено.

3. **Prompt API (произвольные промпты)** (обновлено, высокая уверенность на
   уровне доступности зависимости): `com.google.mlkit:genai-prompt`, на
   момент написания — **beta4**, не alpha (запускался как alpha в октябре
   2025, к моменту `AiCoreTestActivity` уже прошёл до бета). Подключается
   как обычная Gradle-зависимость с `google()` в repositories, без ручного
   allowlist-запроса — во всяком случае ничего похожего на форму доступа
   не встретилось ни в одном источнике при повторном поиске. Принимает text
   или text+image, отдаёт text или structured output — то, что нужно под
   memory extraction (сейчас — `LlmMemoryExtractor`) и классификацию.
   Точная сигнатура API (`Generation.getClient()`, `checkStatus()`,
   `generateContent()`) собрана из поисковых сниппетов, а не из самой
   документации — она тоже недоступна из песочницы (`dl.google.com`/
   `maven.google.com` заблокированы прокси так же, как раньше
   `developers.google.com`), и AAR нельзя было скачать и проверить так, как
   это делалось для `vosk-android` (Maven Central его не зеркалит). Реальная
   проверка компиляции — только через CI этой ветки.

4. **Поддержка русского** (низкая уверенность — **не подтверждено ни одним
   источником**). Официальная документация говорит о оценочных датасетах по
   языкам, но не даёт списка. Для приложения, где русский — один из двух
   основных языков наравне с ивритом, это самый серьёзный неизвестный фактор:
   если качество extraction на русском окажется плохим, модель молча портит
   сохранённые memory-записи, а не просто медленно отвечает. Единственный
   способ узнать — тест на реальном устройстве до какой-либо интеграции.

5. **Устройство** (высокая уверенность для факта запуска, средняя для деталей):
   Pixel 10 Pro явно назван launch-устройством для последней версии Gemini
   Nano. Отдельно существует более широкое требование «Gemini Intelligence»
   (12 ГБ RAM, Nano v3+) — это, по всей видимости, другая, более широкая
   OS-фича (полноценный ассистент), не то же самое, что доступность AICore для
   стороннего Prompt API через ML Kit; в источниках эти два понятия путаются.
   RAM самого устройства (16.3 ГБ по логам этой сессии) в любом случае
   достаточен под оба варианта требований.

6. **Скорость (prefill/generation)** (не подтверждено): ни один источник не
   дал проверяемых цифр tokens/sec конкретно для Prompt API на Pixel 10 Pro.
   Встречавшееся «5-10 tok/s» — это ориентир из статьи не про Nano конкретно,
   не бенчмарк. Нужно мерить самим, тем же подходом, что и в
   `docs/16-stt-benchmark.md`.

### Рекомендация

1. Сделано: `ai.localstudio.app.aicore.AiCorePromptClient` (тонкая обёртка
   над Prompt API — `checkStatus()`/`download()`/`generateContent()`) и
   `AiCoreTestActivity` (Settings → Advanced → "Gemini Nano (AICore)") —
   ручной смоук-тест с прогрессом загрузки и отменой на обоих шагах
   (download и test).
2. Сделано: реальный тест на Pixel 10 Pro прошёл (`checkStatus()` →
   AVAILABLE после скачивания, тестовый промпт на русском дал разумный
   ответ) — единственный блокер из п.4 findings снят.
3. Сделано: `ai.localstudio.app.aicore.AiCoreRuntime` — тонкий
   `ModelRuntime`-адаптер поверх `AiCorePromptClient`, зарегистрирован как
   `CloudProviders.AICORE` рядом с `CloudProviders.LOCAL`, не вместо него —
   у большинства пользователей этого приложения AICore не будет, так что
   GGUF-путь остаётся обязательным фолбэком (и наоборот: устройство без
   Gemini Nano просто не видит его в списке доступных, см. ниже). Подключён
   в `AppContainer.orchestrator()`/`compareCandidates()` тем же способом,
   что и `LOCAL` — отдельная ветка по `provider.id`, а не через
   `cloudCandidates()` (Prompt API не говорит по OpenAI-совместимому
   протоколу).
4. Сознательно НЕ подключено: автоматическая загрузка модели прямо во время
   чата. `AiCoreRuntime.load()` падает быстро (`ModelLoadException`), если
   `checkStatus()` вернул не `AVAILABLE` — `FallbackTextRuntime` просто
   переходит к следующему включённому провайдеру за этот же ход. Причина —
   тот же реальный отчёт с устройства, из-за которого в `AiCoreTestActivity`
   появились прогресс и отмена: молчаливое многоминутное ожидание во время
   обычного сообщения в чате, без какого-либо UI для этого, было бы хуже,
   чем явный переход на резервного провайдера с понятной ошибкой в
   Settings → Advanced, где скачивание уже видно и отменяемо.
5. Сделано: `AiCoreRuntime`/`AiCorePromptClient` теперь принимают и картинку
   (`GenerationRequest.images.firstOrNull()` → `ImagePart` + `TextPart` в
   одном запросе Prompt API, подтверждено сразу по нескольким реальным
   опубликованным реализациям на этой версии SDK — `android/androidify`,
   `google-ai-edge/gallery`, `sceneview/sceneview`). `CloudProviders.AICORE.visionCapable = true`
   — в отличие от `LOCAL`, это фиксированное свойство самого API, а не
   зависит от того, что именно установлено (нет аналога mmproj-файла,
   который надо было бы отдельно скачивать). Только одно изображение за
   запрос — то же ограничение, что уже было у `LlamaCppRuntime`.

### Аудит остальных возможностей AICore/ML Kit GenAI (кроме текста)

Проверено на этой сессии — что из готовых ML Kit GenAI API (кроме Prompt)
реально может заменить другие модели этого приложения:

- **Speech Recognition** (`com.google.mlkit:genai-speech-recognition:1.0.0-alpha1`,
  всё ещё alpha) — реален, два режима: Basic (обычный Android ASR, НЕ Gemini
  Nano) и Advanced (реально Nano, но только Pixel 10/11). Архитектурно
  рассчитан на живой поток (микрофон или файл, поданный с реальной
  скоростью ~32 КБ/с) — **не годится** для батчевой файловой транскрипции
  (`WhisperFileTranscriber`). Пользователь решил пока не подключать это к
  живому микрофону в `TranscribeActivity`, несмотря на то что Pixel 10 Pro
  поддерживает Advanced-режим — риск alpha-API и неясное качество против
  уже настроенного whisper.cpp.
- **Image Description** (`com.google.mlkit:genai-image-description:1.0.0-beta1`)
  — только генерация подписи к фото, **без параметра промпта** — не годится
  как замена VQA (ответ на произвольный вопрос про картинку). Для этого уже
  подключённый Prompt API (см. п.5 выше) — единственный реальный путь.
- **Эмбеддинги** — подтверждённого API для эмбеддингов через AICore для
  сторонних приложений **не существует** (проверено поиском по реальному
  коду, ни одного реального использования не нашлось — то, что есть,
  либо MediaPipe/LiteRT `TextEmbedder`, не AICore/Nano, либо облачный
  Gemini API, не on-device). E5-эмбеддинги в `commercial-memory` заменить
  нечем.
- **Summarization/Rewriting/Proofreading** (все `1.0.0-beta1`) — реальны, но
  с фиксированной формой вывода (например, Summarization отдаёт готовый
  bulleted-список, не свободный текст), так что прямая подстановка в
  `LlmMemoryExtractor` потребовала бы разбора этого формата — уже
  подключённый `AiCoreRuntime` (через Prompt API) естественно закрывает эту
  потребность как обычный текстовый кандидат, отдельная интеграция не нужна.
