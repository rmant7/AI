# 13. Orchestrator

Код: `core/src/main/kotlin/ai/localstudio/core/engine/`

Верхний блок схемы из [01-architecture.md](01-architecture.md) — тот, что
подписан ORCHESTRATOR, — это `Orchestrator` плюс три вспомогательных класса.
Он намеренно тонкий: у каждого решения уже есть владелец, а его работа —
последовательность.

## Путь запроса

```
UserRequest (текст / аудио / изображение)
        ↓
CapabilityRouter            → RoutePlan: какие capability нужны
        ↓
PipelineBuilder             → PipelineSpec: граф стадий
        ↓
PipelineValidator           → граф корректен до запуска
        ↓
PipelineEngine              → топологическое исполнение
        │
        ├─ ModelSelector    → какая модель закрывает эту capability
        ├─ RuntimeManager   → загрузка ровно на время вызова
        ├─ MemoryProvider   → episodic / semantic
        ├─ KnowledgeProvider→ документы
        └─ ContextEngine    → промпт под бюджет токенов
        ↓
Answer (текст + план + граф + контекст + трасса)
```

## Что возвращается наружу

`Answer` содержит не только текст:

| Поле | Зачем |
|---|---|
| `text` | ответ |
| `plan` | какие capability были задействованы и почему (`explanation`) |
| `pipeline` | граф, который реально исполнился |
| `context` | что вошло в промпт и что **не** вошло (`dropped`) |
| `trace` | сколько заняла каждая стадия |

Это прямая противоположность чёрному ящику: пользователь может увидеть, что
ответ строился по трём фрагментам памяти и одному документу, а два документа не
поместились в окно.

## Выбор модели

`ModelSelector` смотрит только на установленные модели — стадия пайплайна не
может ждать многогигабайтную загрузку. Если ни одна установленная модель не
закрывает capability, это отдельная ошибка `NoModelForCapabilityException` с
указанием именно capability, а не модели: UI должен предложить «установить
модель, умеющую OCR», а не «модель не найдена».

`selectAny(listOf(CODING, TEXT_GENERATION))` — деградация вместо отказа: запрос
про код, отмаршрутизированный в `coding`, всё равно получит ответ от общей
модели, если специализированная не установлена.

Перед запуском сохранённого пайплайна можно спросить
`spec.missingCapabilities(selector)` и показать список того, чего не хватает,
не начиная исполнение.

## Память моделей

Каждая стадия берёт модель через `runtimeManager.withModel { }`, то есть
удерживает её ровно на время вызова. Благодаря этому пятистадийный пайплайн
исполняется на бюджете, в который все его модели одновременно не помещаются:
ASR освобождается до того, как загрузится LLM. Проверено тестом
`models are acquired one at a time and fit a budget that could not hold them together`.

Удалённый runtime (`REMOTE_OPENAI`) сообщает нулевой локальный расход — веса
живут на сервере, и менеджеру памяти нечего вытеснять.

## Первые реализации провайдеров

Чтобы всё вышеописанное можно было запустить и протестировать, лежат
простейшие реализации:

- `FileMemoryStore` (модуль `memory`) — лексический поиск по пересечению
  терминов, взвешенный по scope и свежести, персистентный (JSON-файл, не
  только память процесса). Устойчивый факт обгоняет эпизод при равном
  совпадении; между эпизодами решает свежесть; на semantic свежесть не влияет
  вообще (предпочтение, высказанное месяц назад, не менее верно, чем вчерашнее).
- `LocalKnowledgeProvider` + `InMemoryVectorIndex` (в `core`) — parse → chunk →
  embed → cosine → rerank, с перекрытием чанков и явной ошибкой при смене
  размерности эмбеддера.

Обе — заведомо временные (лексический поиск, не эмбеддинги) и обе за
интерфейсом. Их ценность в том, что оркестратор, пайплайны и контекст можно
доводить до ума уже сейчас, а не после
выбора хранилища.
