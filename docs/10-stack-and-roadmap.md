# 10. Стек, режимы разработки и план

## Принцип отбора

Собственная разработка — только там, где она даёт архитектурное преимущество:
Model Manager, Capability Registry, Context Engine, Pipeline Engine и UI. Всё
остальное берётся готовым и прячется за интерфейс.

| Задача | Готовое решение (кандидаты) | Наш код |
|---|---|---|
| Инференс LLM | llama.cpp, MediaPipe/LiteRT, MLC | `ModelRuntime` |
| Speech-to-text | whisper.cpp, sherpa-onnx | `SpeechModelHandle` |
| Каталог моделей | Hugging Face Hub + API | `ModelRegistry`, фильтр под устройство |
| Эмбеддинги | локальная embedding-модель (ONNX) | `EmbeddingModelHandle` |
| Векторный поиск | embedded vector store / SQLite + векторное расширение | `KnowledgeProvider` |
| Долговременная память | Mem0 OSS | `MemoryProvider` |
| RAG | — | тонкий слой: parse → chunk → embed → search → rerank |
| Метаданные, история | SQLite | схема |
| Разработка/отладка | Ollama, llama-server (OpenAI-совместимый API), Open WebUI | `REMOTE_OPENAI` runtime |
| Пайплайны | — | своя JSON-схема + движок |
| UI | — | Android |

Про внешние компоненты: конкретные возможности, лицензии и статус
embedded-режимов надо перепроверять в момент выбора — экосистема edge-инференса
меняется быстрее, чем устаревает архитектура. Именно поэтому каждый из них
заходит через интерфейс: замена стоит одну реализацию.

## Два режима

**Mode A — разработка (десктоп)**

```
Android Studio
      │
      ├── Ollama / llama-server   ← OpenAI-совместимый API
      ├── Open WebUI              ← reference implementation, не часть продукта
      ├── Mem0
      └── vector store
```

Пайплайны, Context Engine и Router отлаживаются здесь, на быстром железе, против
`REMOTE_OPENAI` runtime. Модуль `core` собирается обычной JVM-сборкой без
Android SDK — тесты гоняются за секунды.

**Mode B — устройство**

```
Pixel
 ├── Android UI
 ├── Orchestrator + Router + Context Engine     ← тот же core
 ├── ASR runtime
 ├── LLM runtime
 ├── Vision runtime
 ├── vector store (embedded)
 ├── SQLite
 └── Memory
```

Open WebUI на телефон не переносится. Его ценность — референс поведения и среда
разработки.

## MVP

Пять компонентов снизу и четыре слоя сверху:

```
1. Android UI
2. ASR (whisper.cpp)
3. LLM runtime (llama.cpp)
4. Vector store
5. Memory store

поверх них:
Model Manager + Capability Registry + Pipeline Engine + Context Engine
```

Порядок работ:

| Этап | Содержание | Готовность проверяется |
|---|---|---|
| 0 | Контракты `core`, скорер, менеджер памяти, движок пайплайнов | тесты `core` ✅ |
| 1 | Оркестратор, `REMOTE_OPENAI` runtime, сквозной прогон на десктопе | `:openai:test` — реальный HTTP ✅ |
| 2 | llama.cpp runtime + Model Manager (скачивание, установка, удаление) | модель ставится и отвечает на устройстве |
| 3 | ASR runtime на устройстве, захват микрофона поверх `UtteranceAccumulator` | «говорю → отвечает» |
| 4 | Android UI: Chat, Models, Memory, Knowledge | приложение работает без десктопа |
| 5 | Vision runtime, `photo_analyze` | фото → описание + OCR |
| 6 | SQLite: история, каталог, пайплайны; постоянное хранилище памяти и индекса | состояние переживает перезапуск |
| 7 | Редактор пайплайнов, Model Discovery, экран Models | пользователь собирает свою цепочку |

Этапы 0 и 1 закрыты: `./gradlew test`.

Что именно закрыл этап 1: запрос проходит роутер → `PipelineBuilder` собирает граф →
валидатор → `PipelineEngine` исполняет узлы → `ModelSelector` выбирает модель под
каждую capability → `RuntimeManager` держит её ровно на время вызова → `ContextEngine`
собирает промпт → ответ и запись в память. Голос, изображение и текст идут одним
и тем же путём. Отличие телефона от десктопа — только в том, какой `ModelRuntime`
зарегистрирован.

## Чего не делаем

- **Свой inference-движок** — многолетний проект без выигрыша для этой задачи.
- **Свою векторную БД** — на первом этапе достаточно брутфорс-косинуса в памяти
  (`InMemoryVectorIndex`, микросекунды на тысячах чанков), дальше — готовое
  embedded-решение за тем же `KnowledgeProvider`.
- **Свой memory engine на первом этапе** — но обязательно за своим интерфейсом.
- **Свой маркетплейс моделей** — Hugging Face уже существует.
- **LangChain в ядре Android-приложения** — абстракций больше, чем задачи.
- **Open WebUI как часть мобильного продукта** — это среда разработки.
- **Автоматическое скачивание моделей** — см. [03-model-registry.md](03-model-registry.md).

## Открытые вопросы и риски

1. **Конкуренция за память.** 8 ГБ — это ASR + LLM + VLM, не помещающиеся
   одновременно. `RuntimeManager` описывает политику, но реальные цифры
   `requiredRamBytes` нужно измерять на устройстве: заявленные размеры файлов
   систематически меньше пикового потребления при загрузке. До замера
   используется завышенная оценка, помеченная флагом `isRamEstimated`
   (см. [03-model-registry.md](03-model-registry.md)).
2. **Извлечение памяти стоит инференса.** Mem0-подобная консолидация требует
   LLM-прохода. На телефоне это фоновая работа при зарядке, а не синхронный шаг
   после каждого ответа.
3. **Латентность голоса.** Полный цикл «речь → ASR → retrieval → LLM» на
   мобильном железе измеряется секундами. Потоковая расшифровка и запуск
   retrieval до окончания фразы — не оптимизация, а условие пригодности.
4. **Тепло и батарея.** Длительная генерация приводит к троттлингу; расчётные
   tokens/s деградируют. `performanceIndex` стоит пересчитывать по факту, а не
   считать константой устройства.
5. **Согласованность эмбеддингов.** Смена embedding-модели инвалидирует индекс.
   Версия эмбеддера должна храниться вместе с индексом, а несовпадение —
   приводить к явному предложению переиндексации.
6. **Достоверность бенчмарков.** `benchmarks` в каталоге — внешние данные
   разного качества. Полезнее хранить рядом собственные измерения на устройстве
   и предпочитать их лидербордам.
7. **Лицензии.** Часть популярных моделей имеет ограничения на распространение
   и коммерческое использование; поле `license` в `ModelDescriptor` есть, но
   политика по нему пока не определена.
8. **Флаги нативной сборки решают больше, чем выбор модели.** `-O0` вместо `-O3`
   и отсутствие `armv8.2-a+dotprod+fp16` дают замедление на порядок — это
   проверено, а не гипотеза ([04-runtime.md](04-runtime.md)). Обратная сторона:
   явный ARM-таргет означает SIGILL на устройствах старше ~2017 года, пока не
   сделан runtime-выбор варианта `.so`.
9. **Каталог артефактов — движущаяся цель.** Имена файлов в репозиториях
   квантованных моделей меняются в масштабе недель, поэтому конкретный файл
   разрешается на лету; зашитые имена ломаются молча.
