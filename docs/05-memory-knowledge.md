# 5. Память и знания

Код: `core/src/main/kotlin/ai/localstudio/core/memory/`,
`core/src/main/kotlin/ai/localstudio/core/knowledge/`

## Четыре разных вещи, которые называют «памятью»

```
Working memory    текущий разговор                живёт до конца сессии
Episodic memory   что происходило раньше          «вчера решили делать registry»
Semantic memory   устойчивые знания о пользователе «проект на Kotlin»
Knowledge base    документы пользователя           PDF, Markdown, заметки, код
```

Первые три — `MemoryScope` в `MemoryProvider`. Четвёртая — `KnowledgeProvider`,
и это принципиально другая сущность.

## Почему knowledge отделён от memory

**Память — это то, что система вывела. Знания — то, что пользователь дал.**

Отсюда разные жизненные циклы:

| | Memory | Knowledge |
|---|---|---|
| Источник | извлечено из диалога | загруженный документ |
| Удаление | «забыть факт» | «удалить документ и все его чанки» |
| Точность | вероятностная | цитируемая, со ссылкой на источник |
| Обновление | перезапись факта | переиндексация |
| Смена эмбеддера | не влияет на semantic | требует полной переиндексации |

Свалить это в одно хранилище — значит потерять возможность удалить документ, не
затронув выводы, и наоборот.

## Разделение хранилищ

```
DATA LAYER

     ┌──────────────┬───────────────┬────────────────┐
     │              │               │                │
   SQLite      Memory store    Vector store          │
     │              │               │                │
 conversations   факты          документы            │
 messages        предпочтения    чанки               │
 models          сущности        эмбеддинги          │
 pipelines       связи           метаданные          │
 settings                                            │
 files, jobs                                         │
     │              │               │                │
     └──────────────┴───────────────┴────────────────┘
           application      AI memory        RAG
```

SQLite держит то, что должно быть транзакционным и точным: список моделей,
история, настройки, очередь загрузок. Ни память, ни RAG туда не лезут.

## Mem0: использовать, но не класть в фундамент

Mem0 — разумная первая реализация `MemoryProvider`: не нужно с нуля писать
извлечение фактов, дедупликацию и обновление противоречащих воспоминаний.

Но владельцем памяти он быть не должен:

```
              MemoryProvider          ← интерфейс приложения
                    │
     ┌──────────────┼──────────────┐
     │              │              │
  Mem0OSS      LocalMemory     CloudMemory
```

Причины ровно две, и обе архитектурные:
1. Память переживает не только модели, но и библиотеки. Переход на другое
   хранилище не должен затрагивать Context Engine.
2. Извлечение фактов само по себе требует LLM и эмбеддера — то есть является
   потребителем Model Registry, а не независимым слоем. На телефоне это надо
   уметь откладывать, батчить и выполнять в моменты простоя; интерфейс
   `consolidate(conversationId)` существует именно для этого.

## RAG как отдельный сервис

```
Documents → Parser → Chunker → Embedding → Vector store
                                                 ↓
Query → Embedding → Vector search → Top-K → Reranker → Context Builder → LLM
```

`KnowledgeProvider` (`ingest` / `search` / `delete`) — весь контракт. Внутри —
собственный тонкий слой поверх векторного хранилища; LangChain в ядро
Android-приложения не тянем: абстракций там много, а задача здесь узкая и
понятная.

Выбор векторного хранилища — деталь реализации за интерфейсом. Кандидаты:
embedded-вариант Qdrant, SQLite с векторным расширением. Для первого этапа
хватает второго: отдельная тяжёлая база на телефоне не нужна, пока корпус
документов исчисляется сотнями, а не миллионами чанков. Проверять актуальные
возможности и лицензии embedded-вариантов надо в момент выбора — это движущаяся
цель.

## Что попадает в память автоматически

Ничего — без явного шага. `MemoryUpdate` — отдельный узел пайплайна
(`NodeType.MEMORY_UPDATE`), а не побочный эффект генерации. Пайплайн без этого
узла не пишет память вообще, и это видно на графе.
