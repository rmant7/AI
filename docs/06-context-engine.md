# 6. Context Engine

Код: `core/src/main/kotlin/ai/localstudio/core/context/ContextEngine.kt`

## Роль

```
User message
      +
Conversation
      +
Memory (semantic, episodic)
      +
RAG (документы)
      +
Transcript / Vision
      +
System instructions
      ↓
  CONTEXT ENGINE
      ↓
     LLM
```

Это место, где «продолжи то, что мы делали вчера» превращается в работающий
запрос. Модель ничего не вспоминает — ей передают воспоминание. Именно поэтому
смена модели не стирает историю: помнит система, а не веса.

## Приоритеты

Фрагменты укладываются в бюджет по убыванию приоритета; при равном приоритете —
по релевантности из поиска.

| Источник | Приоритет |
|---|---|
| `SYSTEM` | 100 |
| `USER_MESSAGE` | 90 |
| `TRANSCRIPT` | 85 |
| `VISION` | 80 |
| `TOOL_RESULT` | 70 |
| `CONVERSATION` | 60 |
| `SEMANTIC_MEMORY` | 50 |
| `KNOWLEDGE` | 40 |
| `EPISODIC_MEMORY` | 30 |

Логика порядка: инструкция и сам вопрос не выбрасываются никогда; расшифровка
речи и описание изображения — это и есть вопрос пользователя, просто в другой
модальности; устойчивые факты о пользователе дешевле и полезнее, чем длинные
цитаты из документов; эпизодическая память последняя, потому что она самая
объёмная и самая избыточная.

Приоритет можно переопределить на конкретном фрагменте — например, для
закреплённого пользователем документа.

## Бюджет

```
budget = contextWindow × (1 − responseReserveRatio)   // по умолчанию 0.25
```

Четверть окна резервируется под ответ. Без резерва длинный контекст обрывает
генерацию на середине — сбой, который выглядит как «модель тупит».

Оценка длины по умолчанию — эвристика `≈ 4 символа на токен`, намеренно
пессимистичная: недооценка длины переполняет окно во время генерации,
переоценка лишь отрезает лишний фрагмент. `TokenCounter` подменяется на
настоящий токенизатор выбранной модели, когда он доступен.

## Отброшенное не теряется

`AssembledContext.dropped` содержит всё, что не поместилось, с оценкой длины.
Это нужно для трёх вещей: показать в UI «в контекст не вошло 3 документа»,
подсказать выбор модели с большим окном и отладить пайплайн, который тянет в
контекст лишнее.

Укладка идёт по принципу «влезло — берём»: после отброшенного крупного фрагмента
следующий, более мелкий, всё ещё может поместиться. Это даёт лучшее заполнение
окна, чем остановка на первом непоместившемся.

## Рендер

```
[SYSTEM]
...

[USER_MESSAGE]
...

[KNOWLEDGE]
...
```

Явные метки секций, а не склейка в сплошной текст: модель различает, где
инструкция, где цитата из документа, а где её собственные прошлые выводы.
